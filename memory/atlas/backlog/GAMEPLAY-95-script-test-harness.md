# Aucune couture de test pour instancier un script hors du moteur

`@atlasjs/gameplay` n'expose rien qui permette de monter un script seul. Le paquet a bien son `test/helpers/harness.ts`, mais il est interne au paquet, et son `exports` (`packages/gameplay/package.json:6-12`) ne publie qu'un unique sous-chemin `"."`. Une application qui veut tester ses propres scripts n'a donc que deux leviers : `__bindContext` et l'écriture directe dans les champs.

Deux causes. **(a)** `AtlasScript.__bindContext` (`packages/gameplay/src/scripting/core/AtlasScript.ts:29-31`) exige un `ScriptContext` **complet** — neuf membres entre `ScriptContext.ts:9-18` et `ComponentAccess.ts:6-16` — alors qu'un test n'en utilise que deux ou trois. **(b)** L'injection de props n'est pas atteignable sans un `ScriptManager` monté : `injectProps` est privée (`ScriptManager.ts:246`) et n'est appelée que depuis `attach` (`:82`). Les tests écrivent donc dans les champs privés.

Les chiffres, relevés sur `apps/dino-brawl/test` (29 fichiers, 6210 lignes) : **20 sites** de `as unknown as Record<` répartis sur **17 fichiers** servent à écrire des props à la main — `swordScript.test.ts` en compte 3, `spinAttack.test.ts` 2, quatorze autres fichiers un chacun. Le total des `as unknown as` de la suite monte à **52**, et **35 classes `Fake*`** y sont déclarées. Sur ces fakes, **quatre `FakeContext` locaux** : ceux de `playerMovementScript.test.ts:75` et `playerAnimationScript.test.ts:76` sont **identiques au caractère près** (un `getEntityId` + un `getComponent` sur une `Map`), celui de `playerDashScript.test.ts:97` est le même plus un `getService` sur une seconde `Map`, et celui de `movementEmitter.test.ts:36` est distinct (`getEntityId` + `instantiate` avec journal d'appels). Les quatre sont liés par un `as unknown as ScriptContext`, seul moyen de contourner (a). `aimScript.test.ts` illustre le point suivant : il ne définit **aucun** `FakeContext` et court-circuite entièrement le contexte en écrivant `input`, `camera` et `transform` dans les champs privés du script (`:41-48`).

La conséquence est la plus coûteuse du lot. **Le chemin `injectProps` n'est exercé par aucun test de l'app** — vérifié : zéro occurrence de `ScriptManager`, de `.attach(` ou de `createHarness` dans `apps/dino-brawl/test`. Une classe entière de bugs devient donc structurellement invisible malgré 6210 lignes de specs : les tests posent la valeur *finale* des props directement dans le champ, court-circuitant précisément le code qui décide de cette valeur. Deux défauts l'ont montré, tous deux corrigés depuis dans `packages/gameplay` : l'écrasement d'un défaut de classe par une prop `undefined` (`injectProps` décide désormais sur la valeur, pas sur la présence de la clé), et les incohérences props/métadonnées que `registerScriptMetadata` laissait passer faute d'être typé sur `PropsOf`. Aucun des deux n'a été attrapé par les specs de l'app ; les deux l'ont été par des tests du paquet, écrits à la main faute de couture réutilisable.

Piste : un sous-chemin d'export **additif** `@atlasjs/gameplay/testing`, exposant un `StubScriptContext` (tables de composants et de services, `getEntityId` paramétrable, `instantiate` avec journal — soit l'union des quatre `FakeContext` existants) et un `createScriptHarness(Type, { props, components, services })` qui monte le script par le vrai chemin, injection comprise. Ça suppose d'extraire `injectProps` de `ScriptManager` en fonction pure réutilisable — la méthode ne dépend aujourd'hui que de `this.world` et `this.logger` (`:269`, `:272`), les deux paramétrables. Aucune signature existante n'est touchée ; le coût réel est côté empaquetage : deuxième entrée `tsdown`, deuxième bloc dans `exports`. Alternative moins ambitieuse : garder le harness local à `apps/dino-brawl/test/helpers/`, ce qui dédoublonne les fakes mais laisse `injectProps` inatteignable — donc ne ferme pas la conséquence ci-dessus. C'est le sous-chemin publié qui a le meilleur rapport valeur/coût, parce que lui seul rend le chemin d'injection testable.

**Accroche :** `packages/gameplay/src/scripting/runtime/ScriptManager.ts:246` — extraire `injectProps` en fonction pure est le premier pas, il est mécanique, et c'est lui qui débloque tout le reste ; `StubScriptContext` peut se contenter au départ de l'union des quatre `FakeContext` déjà écrits.

**À rapprocher de :** [[APP-11-player-spec-fakes-duplicated]], qui traite le même symptôme sur le seul périmètre des specs joueur (regroupement dans un `test/game/scripts/player/helpers/` local, sans rien exposer depuis `src/`). Le présent ticket dit que le manque est plus large : la duplication touche 17 fichiers, pas 3, et un helper local ne rend pas `injectProps` testable. Les deux ne sont pas exclusifs — `APP-11` reste le geste rapide, celui-ci la vraie couture.
