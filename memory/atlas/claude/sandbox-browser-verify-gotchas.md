The game app was renamed `apps/sandbox` → `apps/dino-brawl` (2026-07-28); launch config + dev-server name is now `dino-brawl`.

Verifying `apps/dino-brawl` visually in the in-app Browser pane (WebGPU) is slow and flaky:

- **Slow settle**: fps oscillates 0→4→60; the scene needs ~20-25s to settle (the camera lerps onto the player after `onCreate` finishes async asset loads). Budget the wait; a 0/4fps grass-at-origin frame is just mid-init, not a bug.
- **Stale HMR**: Vite HMR serves a STALE scene after edits (the scene builds once in `onCreate`). A plain navigate/reload often runs OLD code. **`preview_stop` + `preview_start` (fresh server) is the reliable way to load changes.**
- **Package `dist/` is what the app runs, NOT `src/` (2026-08-14)**: `apps/dino-brawl` imports workspace packages via their `exports` → `./dist/index.mjs`. So a change in e.g. `packages/gameplay/src/**` is INVISIBLE to the running app until you **`pnpm --filter @atlasjs/gameplay build`** — a server restart alone won't help. This bit a `SpriteRenderSystem` behavior change (not even a public-API change): the `__scene` stash showed the sword still sorting on its own Y until the dist rebuild, after which `sortPrimary` correctly anchored. Rule: after editing ANY package `src`, rebuild that package's dist before browser-verifying the app (broader than the AGENTS.md "public API change" wording).
- **Wedged persistent tab**: a Browser-pane tab kept alive across many `preview_stop`/`preview_start` cycles holds a stale Vite client module graph — even a fresh server + `window.location.reload()` won't clear it. Symptom: recurring HMR errors referencing OLD symbols/paths (e.g. `does not provide an export named 'EcsScene'` after a rename) with an identical `?t=` timestamp, plus a frozen mid-init frame. Fix: **`tabs_create` a NEW tab and navigate there** (or verify on-disk with grep + `preview_logs` — a correct build with a clean-tab render proves the console error is a stale-tab artifact).
- **Scene-graph stash beats screenshots** when pixels are ambiguous: temporarily do `(window as any).__scene = ctx.services.get(NEBULA_RENDERER).scene;` at the end of `onCreate`, then inspect nodes via `javascript_tool` (`getSourceRect()`, `sortingLayer`/`sortPrimary`/`sortSecondary`, `worldMatrix.buffer[12/13]`). This gives ground truth on layer/sort/position.
- **vite.config artifact**: the preview tooling may inject `server: { allowedHosts: true }` into `apps/dino-brawl/vite.config.ts`. Check before committing (not part of any feature).
- `region`-crop zoom isn't supported in the pane (returns the full frame).
- **No WebGPU at all (some sessions)**: on 2026-08-10 the in-app Browser pane reported `navigator.gpu === false` with an empty `<body>` (no canvas) — the WebGPU renderer literally cannot init, so no wait/settle helps and there is NOTHING to screenshot. When `navigator.gpu` is falsy, STOP trying to browser-verify dino-brawl and fall back to the gameplay harness (`test/helpers/harness.ts` boots a real `Engine` with a stub nebula, no WebGPU) — write an integration test there instead. Example: proving `Animator` `finished` → `this.destroy()` self-despawns a one-shot particle end-to-end (`packages/gameplay/test/animator-finish-destroy.test.ts`). Probe first with `javascript_tool`: `JSON.stringify({hasGPU: !!navigator.gpu})`.
- **Preview proxy port mismatch (2026-08-12)**: `preview_start {name:"dino-brawl"}` reported port 57851, but ports 5173/5174 were in use so Vite (autoPort) landed on **5175**; the proxy pointed at the wrong port → the tab showed `net::ERR_CONNECTION_REFUSED` (black, no logs). Check `preview_logs` for Vite's ACTUAL "Local: http://localhost:PORT" line and `navigate` directly to that port. Also the first localhost load can stick on "Policy check in progress"/denied navigation for ~30-60s — retry after a real delay.
- **`document.hidden === true` = frozen loop, black screen, nothing you can do (2026-08-18)**: when the Browser pane is not actually front/visible, the tab reports `document.hidden: true` and the browser throttles rAF to zero. The engine loop is rAF-driven, so the scene never finishes building (logs stop mid asset-load, no MapBuilder lines), the fps overlay freezes at "0 fps"/"4 fps", screenshots are black, and **simulated clicks do nothing** (no update tick consumes the input edge). `setInterval` in injected JS is throttled to ~1/s too, so timer-based probes lie. Probe FIRST, before any wait/restart cycle: `JSON.stringify({hidden: document.hidden})`. If hidden, browser verification is IMPOSSIBLE this session — say so plainly and hand the check to the user instead of burning restarts. Distinguish from the 0x0-viewport case (there `innerWidth` is 0 but `hidden` is false) and from a real black screen (hidden false, fps advancing).
- **0×0 viewport = black screen that is NOT your code (2026-08-12)**: the canvas is `style="width:100vw;height:100vh"`, so if the Browser pane viewport is 0×0 the canvas renders 0×0 → all-black + "0 fps", even though the app booted perfectly. Tell-tale probe: `JSON.stringify({iw:innerWidth, ih:innerHeight, canvas:document.querySelector('canvas')?.clientWidth})` → `iw:0, ih:0, canvas:0`. DOM is correct (`#root>div>[0 fps overlay]+<canvas>`), console shows a full clean boot, `window.__err` empty. Fix: `resize_window {preset:"desktop"}` then re-navigate. After that dino-brawl rendered fine (dino+shadow+run-particles) with 0 errors. Distinguish this from a real black-screen (type-only import) by checking `innerWidth` and for a full plugin-boot log first.

- **`document.hidden` HAS a workaround (2026-08-19) — front the tab before giving up**: the entry above says browser verification is "IMPOSSIBLE this session" when the pane is hidden. That is too pessimistic. `tabs_select {tabId}` **followed by a real `computer` click inside the canvas** un-throttles rAF: the same session went 0 fps/black → **60 fps** and a fully rendered scene in two calls. Do that before concluding anything. The 0-fps black frame with a *complete* boot log (assets loaded, MapBuilder lines present) is the signature of throttling, not of a render bug — a genuinely broken app stops the log mid-boot.
- **Canvas pixel readback works on `apps/webgpu`, NOT on `apps/dino-brawl` (2026-08-19)**: `drawImage(canvas)` + `getImageData` gives real pixels in `apps/webgpu` (loop is `setInterval`, so a frame is always mid-presentation) and returns **fully blank** in dino-brawl (rAF, throttled). So quantitative pixel measurement — the technique that proved the stroke was 7 px on all four sides of a non-square rect — is only available in the `apps/webgpu` demo. In dino-brawl, use the harness screenshot for judgement and put the exact assertion in a unit test instead. Don't burn cycles debugging a "blank readback" there; it is the platform, not the code.

- **A sub-second animation cannot be caught by click-then-screenshot (2026-08-21)**: a `computer` round trip is ~1 s, so a 0.27–0.56 s attack is always over by the time the screenshot lands — you keep photographing the resting pose and conclude nothing. The technique that works: **temporarily multiply the durations by 10 in the source**, restart the dev server, drive the app, observe each phase across several screenshots, then restore the numbers and re-run the suite. On the way back, revert by targeted edit — **never `git checkout <file>`**: on an uncommitted refactor that silently deletes the whole feature (the auto-mode classifier blocked exactly that, correctly).
- **Weapon-sensor hits cannot be verified while the loop sits at 4 fps (2026-08-21)**: `dt` is ~250 ms, so the blade teleports past the target between physics steps and `onTriggerEnter` never fires — an attack reads as a miss even with the tip visually on the enemy. Front-the-tab + click sometimes recovers 60 fps, sometimes not; when it doesn't, say the hit path was not observed rather than reporting a miss as a finding. Synthetic `keydown` to walk closer also silently fails at that framerate (the player does not budge). The pose/orbit is still verifiable — that only needs frames, not physics.

**Why:** In the Y-sort session I burned ~15 reload cycles concluding "the tree sprite doesn't paint" — it DID paint; the real causes were a wrong crop region + stale HMR serving old code. The scene-graph stash would have shown the truth (nodes present, correct sort) in one call.

**How to apply:** For any sandbox visual check — restart the dev server after edits (don't just reload), wait ~20-25s to settle, and reach for the `__scene` stash + `read_console_messages` probes before concluding a render bug. See [[vite-type-only-imports]] for the related type-only import black-screen trap.
